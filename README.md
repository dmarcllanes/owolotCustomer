# Owolot landing page

The public landing page for Owolot, a local-first personal finance app for iOS
and Android. The site uses FastHTML with Starlette/ASGI, Uvicorn, server-rendered
HTML, and custom CSS. Brand artwork is served from `assets/`.

## Local development

Requirements: Python 3.12 and [uv](https://docs.astral.sh/uv/).

```sh
uv sync --extra test
uv run uvicorn main:app --reload
```

Open <http://127.0.0.1:8000>. Run the tests with:

```sh
uv run pytest
```

## Local configuration

The app listens on `0.0.0.0` and uses `PORT` (default `8000`). Beta requests
are stored at `DATABASE_PATH` (default
`data/beta_requests.sqlite3`). Set both `BETA_ADMIN_USERNAME` and
`BETA_ADMIN_PASSWORD` in the environment to enable request submissions and the
`/admin/beta` dashboard; requests are rejected until both are configured. These
settings are provided automatically by the AWS stack in production.

## AWS deployment

The GitHub Actions workflow builds and publishes the Docker image to Amazon
ECR, then deploys `infra/aws/stack.yaml` to ECS Fargate. The stack provisions
an application load balancer, a CloudFront HTTPS endpoint, an encrypted EFS
filesystem for SQLite, and an auto-generated admin credential in AWS Secrets
Manager. Requests reach the load balancer only from CloudFront; HTTP viewers
are redirected to HTTPS. The ECS service runs one task so the SQLite database
has a single application instance.

The deployment uses AWS resources that incur charges, including CloudFront,
an application load balancer, Fargate, EFS, and ECR storage. Review current
regional pricing and your account's free-tier eligibility before deploying.
There is no custom domain or ACM certificate configured; CloudFront provides
the initial HTTPS URL.

### One-time GitHub and AWS setup

1. In AWS IAM, add the GitHub Actions OIDC identity provider:
   `https://token.actions.githubusercontent.com` with audience
   `sts.amazonaws.com` (skip this if it already exists).
2. Create an IAM role trusted for web identity from that provider. Restrict its
   trust policy to the repository and deployment branch:

   ```json
   {
     "Version": "2012-10-17",
     "Statement": [{
       "Effect": "Allow",
       "Principal": {
         "Federated": "arn:aws:iam::<AWS_ACCOUNT_ID>:oidc-provider/token.actions.githubusercontent.com"
       },
       "Action": "sts:AssumeRoleWithWebIdentity",
       "Condition": {
         "StringEquals": {
           "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
           "token.actions.githubusercontent.com:sub": "repo:dmarcllanes/owolotCustomer:ref:refs/heads/main"
         }
       }
     }]
   }
   ```

3. Give this role only the deployment permissions required by the workflow and
   stack: create/push to the `owolot-customer` ECR repository; deploy and read
   the `owolot-customer` CloudFormation stack; inspect EC2 managed prefix
   lists; create the VPC, security groups, EFS, ECS, load-balancer, CloudFront,
   log, Secrets Manager, and IAM resources declared in the template; and pass
   the stack's ECS task roles to `ecs-tasks.amazonaws.com`. Scope permissions
   to this stack and its resources where AWS supports resource-level
   permissions. Do not use long-lived AWS access keys or attach unrestricted
   administrator permissions to a public-repository workflow role.
4. In GitHub repository **Settings → Secrets and variables → Actions**, add:

   | Name | Type | Value |
   | --- | --- | --- |
   | `AWS_REGION` | Repository variable | The AWS region to deploy into, for example `us-east-1`. |
   | `AWS_ROLE_ARN` | Repository secret | The ARN of the GitHub OIDC deployment role. |

5. Push to `main` or run **Actions → Deploy to AWS → Run workflow**. The first
   deployment creates the ECR repository and all application resources. The
   workflow prints the CloudFront website URL and admin URL at completion.

### Admin access and persistent data

- The admin password is generated by Secrets Manager; it is not printed by the
  deployment workflow. Find the `AdminCredentialsSecretArn` stack output, then
  retrieve the secret from a trusted local terminal:

  ```sh
  aws secretsmanager get-secret-value \
    --secret-id <AdminCredentialsSecretArn> \
    --query SecretString \
    --output text
  ```

  Keep the result private. The secret contains the admin username and password
  used at `/admin/beta`.
- The stack mounts an encrypted EFS access point at `/data` and sets
  `DATABASE_PATH=/data/beta_requests.sqlite3`. EFS backup is enabled, and
  CloudFormation retains the filesystem and admin secret if the stack is
  deleted. Review the AWS Backup plan and recovery requirements for your
  account.
- The site and admin page are served through CloudFront. HTTP requests redirect
  to HTTPS, and the load balancer accepts origin traffic only from
  CloudFront's AWS-managed prefix list.
- Rotate the dashboard password in Secrets Manager when needed, then force a
  new ECS deployment so the task receives the rotated secret.
- Decide and document a retention/deletion schedule for beta request emails
  before launch. The admin page is read-only and does not delete requests;
  until a deletion workflow is added, an operator must manage retention in the
  EFS-backed SQLite database.

## Content and launch checklist

- The page describes product behavior based on the current product brief; update
  `main.py` when verified app behavior changes.
- `/beta` accepts an email address and iOS/Android selection after explicit
  consent. Requests are stored in SQLite; `/admin/beta` lists the latest 500
  requests for a manually authenticated admin. It does not send email or grant
  store access automatically. Both admin credential variables must be set
  before a beta request can be accepted; otherwise the form shows that requests
  are unavailable.
- Decide and document a retention/deletion schedule for beta request emails
  before launch. The admin page is read-only and does not delete requests;
  until a deletion workflow is added, an operator must manage retention in the
  SQLite database directly.
- Configure and verify the iOS TestFlight and Android Google Play testing
  tracks before sending installation instructions. No invite links are
  published on the site.
- To create an iOS invite: in App Store Connect, open the app's TestFlight
  page, add a tester group and build for external testing, then enable a public
  link for that group after completing Apple's required review steps. You can
  also invite testers by email. Send the resulting invite to approved
  applicants yourself.
- To create an Android invite: in Google Play Console, configure a closed or
  internal testing track, add the tester email/group or enable its opt-in
  link, and publish the test release. Send approved applicants the appropriate
  opt-in and Play installation instructions yourself.
- No production domain is confirmed, so the page intentionally has no canonical
  URL.
- A publisher-approved privacy policy, support contact, publisher identity, and
  any legal terms have not been provided. The page labels its privacy section
  as an overview and does not invent those destinations or details.
- `PRODUCT_NAME` in `main.py` is the single source for the displayed product
  name.
